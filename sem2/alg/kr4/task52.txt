Задание 5

Нужно выбрать, как хранить архив оценок студентов. В архиве до 10 миллионов записей.
В каждой записи есть id студента и оценка от 2 до 5.

Запросы всего два:

1. Найти оценку студента по id.
2. Узнать, сколько студентов получили заданную оценку.

Так как запросы выполняются часто, обычный перебор по всем записям здесь быстро станет неудобным. На 10 миллионах записей линейный поиск будет слишком медленным.


Способ 1. Хеш-таблица и счетчики оценок

Идея простая: для поиска оценки по id хранить хеш-таблицу:

id студента -> оценка

А для второго запроса отдельно хранить массив счетчиков:

count[2], count[3], count[4], count[5]

Например, если добавили студента с оценкой 5, то мы записываем его оценку в хеш-таблицу и увеличиваем count[5].

Как работают запросы:

1. Найти оценку по id.

Берем id как ключ и обращаемся к хеш-таблице.

Средняя сложность: O(1).
Худшая сложность: O(N), если случится много коллизий, но на практике при нормальной хеш-функции поиск почти всегда работает за O(1).

2. Посчитать студентов с заданной оценкой.

Просто обращаемся к нужному счетчику.

Например:

count[4]

Сложность: O(1).

Память:

Хеш-таблица хранит все id и оценки. Память получается O(N). Но у хеш-таблицы есть накладные расходы: корзины, служебные данные, запас под расширение. При 10 миллионах записей это уже заметно.

Массив счетчиков почти ничего не стоит, потому что оценок всего четыре.

Плюсы:

- самый быстрый поиск оценки по id;
- подсчет студентов с нужной оценкой тоже O(1);
- хорошо подходит, если запросов много.

Минусы:

- памяти нужно больше, чем для обычного массива;
- в худшем случае хеш-таблица может работать медленнее из-за коллизий.


Способ 2. Отсортированный массив записей и счетчики оценок

Можно хранить записи в массиве, отсортированном по id студента:

(id студента, оценка)

Дополнительно снова храним count[2], count[3], count[4], count[5].

Как работают запросы:

1. Найти оценку по id.

Так как массив отсортирован, используем бинарный поиск.

Сложность: O(log N).

Для 10 миллионов записей это около 24 сравнений, то есть тоже вполне быстро.

2. Посчитать студентов с заданной оценкой.

Берем значение из массива счетчиков.

Сложность: O(1).

Память:

Массив хранит только сами записи. Накладных расходов меньше, чем у хеш-таблицы.
Итоговая память все равно O(N), но на практике такой вариант компактнее.

Плюсы:

- экономнее по памяти;
- поиск по id остается достаточно быстрым;
- удобно, если архив в основном читают, а не постоянно изменяют.

Минусы:

- поиск медленнее, чем в хеш-таблице;
- если часто добавлять новые записи, придется поддерживать сортировку.


Способ 3. Обычный неотсортированный массив

Самый простой вариант - просто хранить все записи подряд:

(id студента, оценка)

Как работают запросы:

1. Найти оценку по id.

Нужно пройти по массиву, пока не найдется нужный студент.

Сложность: O(N).

2. Посчитать студентов с заданной оценкой.

Если не хранить счетчики, придется пройти по всем записям и посчитать.

Сложность: O(N).

Можно добавить счетчики оценок, тогда второй запрос станет O(1), но поиск по id все равно останется O(N).

Память:

Памяти нужно мало: только массив записей. Но скорость слишком слабая для частых запросов.

Плюсы:

- самая простая реализация;
- почти нет дополнительных расходов памяти.

Минусы:

- поиск по id медленный;
- для 10 миллионов записей и частых запросов вариант плохой.


Сравнение способов

1. Хеш-таблица + счетчики

Поиск оценки по id: O(1) в среднем.
Количество студентов с оценкой: O(1).
Память: O(N), но с заметными накладными расходами.

Это лучший вариант по скорости.

2. Отсортированный массив + счетчики

Поиск оценки по id: O(log N).
Количество студентов с оценкой: O(1).
Память: O(N), обычно меньше, чем у хеш-таблицы.

Это хороший вариант, если память важнее максимальной скорости.

3. Обычный массив

Поиск оценки по id: O(N).
Количество студентов с оценкой: O(N), если нет счетчиков.
Память: O(N), дополнительных расходов мало.

Для этой задачи вариант слабый, потому что запросы выполняются часто.


Trade-off между скоростью и памятью

Хеш-таблица дает самый быстрый поиск, но тратит больше памяти.
Отсортированный массив экономит память, но поиск будет O(log N), а не O(1).
Обычный массив проще всего, но по скорости он не подходит для большого архива.

Если система должна отвечать как можно быстрее, я бы выбрал хеш-таблицу и счетчики.
Если память ограничена очень жестко, тогда лучше взять отсортированный массив и счетчики.


Итоговый выбор

Оптимальное решение для частых запросов:

1. Хеш-таблица:

id студента -> оценка

2. Массив счетчиков:

count[2], count[3], count[4], count[5]

Почему этот вариант лучше:

- оценку студента по id можно найти за O(1) в среднем;
- количество студентов с заданной оценкой можно получить за O(1);
- счетчики занимают O(1) памяти, потому что оценок всего четыре;
- при большом числе запросов скорость важнее, чем небольшая экономия памяти.

Ответ:

Для архива лучше использовать хеш-таблицу и массив счетчиков оценок.

Сложность запросов:

- найти оценку по id: O(1) в среднем;
- найти количество студентов с оценкой 2, 3, 4 или 5: O(1).

Память:

- O(N) для хранения id и оценок;
- O(1) для счетчиков.

Если памяти не хватает, можно заменить хеш-таблицу на отсортированный массив записей. Тогда поиск оценки по id будет O(log N), зато хранение будет компактнее.
